## 1. 프로젝트 소개

![[Pasted image 20261105184409.png]]![[Pasted image 20261105171702.png]]

안심길은 가장 빠른 길이 아니라 가장 덜 힘든 길을 찾아 주는, 언덕 동네 어르신을 위한 도보 길안내 웹앱이다.

성남 원도심(수정구·중원구)은 1970년대 광주대단지 이주 정착지로 산비탈에 급하게 만들어진 동네다. 그래서 지금도 언덕과 계단, 좁은 골목, 인도 없는 길이 많다. 그런데 지도 앱의 도보 길찾기는 **가장 빠른 길**이 기준이라 계단이 197단이나 있는 길도 그대로 추천한다. **가까운 길이 편한 길은 아니다**라는 생각에서 이 프로젝트를 시작했다.

|항목|내용|
|---|---|
|서비스 지역|성남시 중원구 은행동 (3개 구역)|
|주요 대상|고령 보행자|
|서비스 형태|모바일 웹앱(PWA)|
|차별점|직접 걸어서 조사한 보행 데이터 활용|

예를 들어 은행근린공원 서쪽입구에서 구현진약국까지 가장 짧은 길에는 계단 197단이 있다. 안심길은 같은 12분 안에 계단 없는 길로 안내한다.

길을 찾을 때는 계단·오르막·신호 없는 횡단보도·인도 없는 길을 고려해 덜 힘든 길을 추천하고, 최대 3개 경로를 시간·거리·계단 수·높이 변화로 비교할 수 있게 했다. 안내는 "50m 앞"이 아니라 "유할인마트 정류장 앞에서 오른쪽으로 도세요"처럼 장소 이름으로 하고, 단계마다 음성으로 읽어 준다. 그 밖에 이런 기능이 있다.

- **말로 목적지 찾기**: "구현진약국 가줘"라고 말하면 바로 길을 찾는다.
- **AI 사진 제보**: AI가 사진 속 계단을 먼저 찾고, 사용자가 확인한 내용만 길찾기에 반영한다.
- **맞춤 설정**: 계단 회피, 돌아가는 정도(1.3배 / 2배), 글자 크기 5단계를 고를 수 있다.

## 2. 프로젝트 과정

팀 구성은 정서윤(기획·앱 디자인), 김다은(발표·발표자료 제작), 박시후(앱 개발·AI 학습, 팀장)이다. 예선 계획서를 제출하고 예선을 통과한 뒤, 약 한 달간 본선(10.24)을 준비했다.

```
주제 선정 → 예선 계획서 → 예선 통과 → 현장조사 → 데이터 구축
→ 경로 알고리즘 → 앱 개발 → AI 학습(1차·2차) → AI 앱 탑재
→ 테스트 → 시연 영상 · 발표자료 → 본선 발표
```

### 2-1. 기획

처음에는 도보 여행 코스 추천과 미션·포인트를 결합한 앱을 구상했지만, 성남 원도심의 산비탈 이동 불편을 해결하는 고령자 보행경로 안내로 주제를 바꿨다.

성남시 연령별 인구를 동 단위로 분석해 은행2동의 65세 이상 비율이 늘고 있다는 것을 확인했다. 고령친화도시 정책과 보행안전 기본계획에서는 서비스의 공공적 근거를 찾았다.

주민 설문과 인터뷰도 진행했다. 가장 많이 나온 불편은 언덕·계단과 좁은 길이었고, 인터뷰 내용은 기능 설계에 그대로 반영했다.

|인터뷰 내용|반영한 기능|
|---|---|
|좁은 길·불법주차가 더 위험하다|인도 없는 길에 더 높은 점수|
|건물 기준으로 알려주면 쉽다|장소 이름 안내, 꺾는 곳 줄이기|
|1.3배까지는 돌아가도 괜찮다|돌아가는 정도 설정 (1.3배 / 2배)|

### 2-3. 디자인![[Pasted image 20261105171057.png]]

흰 배경에 초록 포인트 색 하나만 쓰고, 글씨와 버튼은 크게 만들었다. 색만으로 구분하지 않고 아이콘·선 모양·글자를 함께 사용했다.

색은 초록에서 여러 시안과 네이비를 거쳐 최종적으로 다시 초록으로 돌아왔다. 안내 화면은 자동으로 넘어가는 방식이었는데, 걷는 속도에 맞춰 사용자가 한 단계씩 넘기는 방식으로 바꿨다.

### 2-4. 개발

#### 길 데이터 제작

갈림길은 점, 길은 선으로 잇는 그래프를 Python으로 만들었다. OpenStreetMap 골목길 565개를 추가해 보기도 했지만, 계단·경사를 모르는 길로 안내하면 위험하기 때문에 직접 확인한 길만 사용했다. 최종적으로 길 75개, 장소 35곳, 서로 이어진 장소 쌍 182개가 만들어졌다.

#### 덜 힘든 길 계산

길마다 힘든 정도 점수를 매기고, 다익스트라 알고리즘으로 점수 합이 가장 작은 길을 찾았다. 경사 부담은 Tobler 보행속도 함수로 계산했다.

일반 다익스트라는 어느 방향으로 꺾었는지 알 수 없는 구조라서, "지점 + 들어온 길"을 한 상태로 보고 탐색하도록 바꿨다. 그 결과 꺾는 횟수가 경로당 2.3회에서 1.5회로 줄었다.

예상 시간은 어르신 걸음(분당 50m)에 경사·계단·신호 대기를 더해 계산했다.

#### 앱 제작

프레임워크 없이 HTML · CSS · JavaScript로 구현했고, 화면을 그리는 렌더러를 직접 만들었다. PWA로 만들어 홈 화면 설치와 오프라인 실행을 지원했고, Netlify로 배포해 QR로 접속할 수 있게 했다.

#### AI 학습
![[예시_정답vsAI (1).png]]
사진을 픽셀 단위로 계단·인도·차도로 나누는 DeepLabV3+ 모델을 AI Hub 「인도보행 영상」 데이터로 학습했다. 계단 사진이 전체의 3.9%뿐이었고 계단 표시 중 상당수가 맨홀·보도블록이었기 때문에, 372장을 직접 검수해 진짜 계단 194장만 사용했다.

1차 모델은 시험 점수는 괜찮았지만 은행동 현장 사진에서 하늘을 도로로 칠하는 문제가 있었다. 원인 4가지를 찾아 2차 학습에서 수정했다.

- 배경 사진 부족 → 계단 없는 사진 1,200장 추가
- 세로 사진이 찌그러져 들어감 → 사진 비율 유지
- 비슷한 장면으로 시험해 점수 부풀림 → 촬영 폴더 단위로 학습·시험 분리
- 인도·골목 미구분 → 인도 / 골목 / 차도 분리

그 결과 하늘·건물을 바닥으로 칠하는 비율이 9.9%에서 3.5%로 줄었고, 현장 25개 구간 중 23개에서 계단 유무가 일치했다.

#### AI 앱 탑재

학습한 모델을 ONNX로 변환하고 8비트로 압축해 107MB에서 27MB로 줄였다(변환 전후 일치율 98.6%). onnxruntime-web으로 휴대폰 브라우저 안에서 실행하기 때문에 서버가 필요 없고 사진이 밖으로 나가지 않는다.

이 모델로 사진 제보 기능을 만들었다. AI가 먼저 계단을 판단하고 사용자가 확인한 것만 반영하는 구조라서, AI가 틀려도 잘못된 길로 안내되지 않는다.

#### 테스트

Playwright로 첫 화면부터 사진 제보, 다시 길찾기까지 자동으로 확인했다. 이 과정에서 제보한 작은 계단 때문에 오히려 197단 계단 길로 안내되던 버그와, 아이폰에서 글자가 파랗게 보이던 문제를 찾아 고쳤다.

|영역|기술|
|---|---|
|앱|HTML · CSS · JavaScript, PWA|
|경로|Dijkstra, Tobler 보행속도 함수|
|지도 · 데이터|OpenStreetMap, 성남시 공공데이터, Python|
|AI|PyTorch, Google Colab, DeepLabV3+, ONNX, onnxruntime-web|
|음성|Web Speech API|
|테스트 · 배포|Playwright, Netlify|

## 3. KPT 회고

### Keep (잘한 점)

- 어떤 서비스를 개발하면서 직접 발로 뛰어 현장 조사를 하며 데이터를 만든 건 처음이었는데, 조사하며 계단 수나 경사, 고장 난 신호등 등을 직접 조사하며 생각보다 경사가 엄청나고 걷기 너무 힘든 길이 많았어서 더 서비스 개발에 몰입할 수 있었다.
- 현장 조사를 하며 인터뷰 및 설문조사를 함께 했는데, 설문조사 시 얻은 데이터가 생각보다 발표 및 앱 개발에 큰 도움이 되었다. 
- 중간중간 AI 오류가 정말 많이 났다. 사진을 분석해서 계단 및 오르막이 어느 부분에 있는지 직접 AI가 색칠해야 했는데, 이 때 계속 AI가 잘못된 값을 내놓았는데도 계속 포기하지 않고 여러 데이터들을 넣으며 학습시킨 후 꽤 정확도가 있는 분석 결과를 내놓을 수 있었다.
- 정확하지 않은 데이터가 사용자에게 미칠 피해에 대해 더 깊게 생각했고 개발에 반영했다. 정확하지 않은 데이터를 넣으면 앱 자체는 좀 더 완성도 있어보였겠지만, 사용성에 조금 더 집중하였다. 정확하지 않은 기능을 과감하게 뺀 게 잘한 것 같다.

### Problem (개선할 점)
- 어르신 사용 테스트를 하지 못했다. 발표 때 Q&A 시간에도 실제 어르신에게 테스트를 해봤냐는 질문을 받았는데, 사용성 테스트를 했는가 안했는가가 생각보다 꽤 중요한 점수요소로 작용하는 것 같았다. 다음에 공모전을 할 때는 서비스를 사용자에게 테스트 해보게 하는 것도 고려해봐야 할 것 같다.
- 서비스 범위가 좁았다. 성남시 공모전이었는데 성남시 내의 작은 동인 은행동밖에 조사하지 못해서 데이터가 은행동밖에 없었다. 제보 또한 서버 없이 각 휴대폰에만 저장되기 때문에 MVP라는 걸 고려해도 서비스가 조금 부족했던 것 같다. 이를 위해 사용자 제보 기능을 넣은 거지만 다른 보행 관련 공공 데이터가 조금이라도 더 존재했으면 서비스의 범위를 좀 더 넓힐 수 있지 않았을까 하는 아쉬움이 남아있다.
- 일정 관리가 아쉬웠다. 본선 진출이 갑작스러웠기도 하고, 내신 기간과 완벽히 겹쳐서 시간이 조금 더 많았다면 AI 관련 기능을 좀 더 추가할 수 있지 않았을까 싶다.
